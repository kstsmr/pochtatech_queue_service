# Безопасность MVP

## Границы проверки

Проверки выполняются только против локального Docker Compose стенда. Они не
предполагают нагрузочные атаки на GitLab, Codenrock или другие внешние системы.
MVP не хранит персональные данные клиента: талон доступен по непрозрачному
токену, а QR отделения содержит только публичный deep-link и почтовый индекс.

## Реализованные меры

- PostgreSQL и Redis не публикуют порты на хост и находятся во внутренней сети.
- Frontend отделён от сети данных; к PostgreSQL и Redis подключаются только
  backend и worker.
- Контейнеры приложения работают без root, без Linux capabilities, с
  `no-new-privileges` и read-only root filesystem.
- SQL выполняется с bind-параметрами. Динамический фрагмент приоритета выбирается
  только из фиксированного набора серверных alias.
- Клиентские, операторские и руководительские данные изолируются по токену,
  роли и `branch_id`.
- Служебные токены хранятся в `sessionStorage`, в базе хранится только их hash.
- PIN хешируется PBKDF2-HMAC-SHA256 с индивидуальной солью; после пяти ошибок
  учётная запись временно блокируется.
- Redis ограничивает частоту входа, создания публичных талонов и вызовов
  demo-интеграции. При недоступности limiter изменяющие запросы закрываются.
- API не возвращает исходные значения, не прошедшие валидацию.
- Nginx ограничивает размер тела запроса и выставляет CSP, anti-framing,
  MIME-sniffing, referrer и permissions policies.
- Browser WebSocket принимает только настроенные origins и затем требует токен
  талона первым сообщением.
- Production/staging запуск отклоняет demo-placeholder секреты.

## Воспроизводимая проверка

После запуска стенда:

```sh
python3 tools/check_security.py
```

Статический аудит зависимостей и Python-кода:

```sh
cd frontend && npm audit
python3 -m pip_audit -r backend/requirements.txt
bandit -r backend/app -ll
```

`pip-audit` и `bandit` являются инструментами аудитора и не входят в runtime
зависимости приложения.

## Ограничения demo-контура

Для публичного размещения перед Nginx нужен TLS ingress/reverse proxy, секреты
нужно передавать из менеджера секретов, а demo PIN-аутентификацию заменить
корпоративным SSO с MFA. Для регионального развёртывания rate-limit и сессии
должны использовать отказоустойчивый Redis-кластер соответствующей ячейки.
Миграции и runtime API должны подключаться к PostgreSQL разными ролями, причём
runtime-роль получает только необходимые права на рабочую схему.
Логи следует отправлять в централизованное хранилище с маскированием и политикой
срока хранения. Эти требования не подменяются локальным security smoke test.
