# QR-вход в очередь

## Формат и безопасность

QR-код отделения содержит стабильную публичную ссылку:

```text
https://queue.example.ru/qr?branch=101000
```

В ссылке есть только публичный шестизначный код отделения. В QR не помещаются
идентификатор талона, токен сессии, выбранная услуга или персональные данные.
Публичный адрес клиента задаётся переменной `PUBLIC_CLIENT_URL`. В локальной
демонстрации QR-стенд также позволяет явно указать адрес компьютера в Wi-Fi-сети;
override принимается сервером только в `development`/`test` и проходит проверку
как HTTP(S)-origin без пути, query, credentials и fragment.

SVG генерируется сервером через Segno по запросу
`GET /api/branches/{branch_id}/queue-qr.svg`. Перед генерацией API проверяет, что
отделение существует и активно. Результат можно печатать без растеризации;
браузеру разрешено кешировать его один час.

Для демонстрации откройте `/demo/qr`, выберите отделение, проверьте поле «Адрес,
который откроется на телефоне» и используйте один из
трёх вариантов: отсканируйте плакат камерой другого устройства, скачайте SVG или
нажмите «Открыть как клиент». Последний вариант воспроизводит результат
сканирования на одном компьютере. Метаданные стенда доступны через
`GET /api/branches/{branch_id}/queue-qr`.

### Проверка с телефона

Если стенд открыт через `localhost`, он явно предупреждает, что такой QR не
откроется на телефоне. Для разовой проверки введите в поле стенда адрес вида
`http://192.168.1.50:3000`. Для постоянной проверки телефоном в той же доверенной
Wi-Fi-сети укажите в `.env`:

```dotenv
PUBLIC_CLIENT_URL=http://192.168.1.50:3000
FRONTEND_BIND_HOST=0.0.0.0
```

Замените `192.168.1.50` на LAN-IP компьютера и перезапустите контейнеры. Backend
отдельно наружу открывать не требуется: запросы `/api` проксирует frontend.
После теста верните `FRONTEND_BIND_HOST=127.0.0.1`. Не используйте этот режим в
недоверенной сети без HTTPS и сетевого экрана.

## Выдача талона

1. После сканирования клиент открывает `/qr?branch=<код>`.
2. Интерфейс проверяет код через API, показывает подтверждённые название и адрес
   отделения и не заставляет повторно вводить код с плаката.
3. Клиент выбирает услугу и отправляет `POST /api/queue/join` с новым UUID в
   заголовке `Idempotency-Key`.
4. Сервер находит активное отделение и услугу, берёт транзакционную advisory-lock
   по ключу запроса и создаёт сессию, талон и событие одной транзакцией.
5. Повтор того же запроса возвращает тот же талон. Использование ключа с другим
   телом отклоняется с `409 idempotency_key_reused`.

Номер талона и порядок очереди назначаются PostgreSQL identity-последовательностями.
Сырой токен сессии не хранится в БД: сохраняется только SHA-256 hash. После
создания токен остаётся на устройстве клиента и используется для восстановления
талона.

## Статус на смартфоне

Страница талона открывает `/api/ws/tickets/{ticket_id}` через тот же frontend
origin. Токен не попадает в URL или журналы: клиент передаёт его первым сообщением
после установки WebSocket. Канал отправляет состояние только при изменении и
закрывается после завершения талона. Nginx проксирует WebSocket Upgrade.

При разрыве канала интерфейс автоматически опрашивает REST API раз в пять секунд
и пытается восстановить WebSocket. При приближении очереди и вызове к окну
показывается браузерное уведомление (после согласия пользователя), а на
поддерживаемом смартфоне включается короткая вибрация. Основной статус и номер
окна всегда отображаются внутри страницы, даже если системные уведомления
запрещены или недоступны.

## Демонстрационные допущения

Код отделения считается размещённым внутри соответствующего отделения. Геолокация
и защита от удалённого сканирования не входят в MVP. В промышленной версии можно
добавить короткоживущую подпись или проверку геозоны, не меняя транзакционную
логику выдачи талона.
