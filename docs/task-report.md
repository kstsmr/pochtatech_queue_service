# Первые три задачи тимлида

Область: первые три пункта раздела «Тимлид / Backend-архитектор» в приложенном
плане. Это этап проектирования, а не первые три пользовательских сценария.

1. ER-схема: docs/data-model.md + SQL-спецификация docs/schema.sql.
2. Модель талона: docs/ticket-lifecycle.md, включая состояния, ограничения и историю.
3. Правила приоритета: config/priority.yaml, docs/priority-algorithm.md и валидатор.

## Проверено фактически

- `python3 tools/check_priority.py`: успешно.
- `python3 -m unittest discover -s tests -v`: 8 тестов, успешно.
- Проверены пропущенные/лишние ключи, неверные типы и диапазоны, неизвестная
  версия, нулевые early/grace, неверное расположение приоритетов.
- Вручную сверены составные внешние ключи, активное назначение окна, модель
  состояний и соответствие конфигурации описанным правилам.

В текущем окружении отсутствуют исполняемые Docker и psql. SQL не применялся
к PostgreSQL: синтаксис, ограничения и гонки ещё требуют проверки на сервере.
Тесты валидатора не являются тестами алгоритма выбора или очереди.
Frontend в этой задаче не менялся. CI/CD не добавлялся.

## Прослеживаемость обязательных проверок ТЗ

| Проверка | Заложенное решение | Что ещё реализовать и проверить |
| --- | --- | --- |
| 1. Предзапись | slots, capacity, booked, scheduled_time | API и конкурентная бронь последнего места |
| 2. QR | source=qr, сессия, waiting | Проверка кода и выдача через API |
| 3. Вызов | lock отделения, совместимость услуги | Реальная транзакция call-next |
| 4. Два окна | lock + UNIQUE активного окна | Параллельные запросы на PostgreSQL |
| 5. Закрытие | called возвращается; serving завершается в draining | Гонки close/call и force-close |
| 6. Перенаправление | target_window отдельно от назначения | API и снятие ограничения при закрытии цели |
| 7. Restart | Состояние в БД, журнал, persisted outbox | Volumes, миграции, восстановление worker и сессий |
| 8. Сбой уведомлений | Outbox, lease, дедупликация | Демо-адаптер, таймаут, повтор доставки |
| 9. Конкурентная выдача | Identity + idempotency + capacity | Нагрузочный тест и повтор после обрыва ответа |
| 10. Аналитика | ticket_events и window_events | Расчёты интервалов, API и экран руководителя |

Остальные обязательные сценарии учтены в модели: отмена, возврат, начало/окончание
обслуживания, источник талона, проблемы, управление услугами и правилами,
восстановление сессии. ETA, WS, уведомления о приближении, ролевой доступ и UI
ещё предстоит реализовать. Итоговое соответствие ТЗ не заявляется до их проверки.

## Согласованные здесь уточнения плана

- returned/redirected являются событиями; после них состояние waiting.
- booked отделяет будущие записи от активной очереди.
- Обычное закрытие serving использует draining; прерывание отдельной командой.
- Priority level вычисляется при выборе, иначе повышение по времени устаревает.
- 20 минут для walk_in — порог повышения, не безусловная гарантия времени вызова.
- Секрет сессии не передаётся в URL; роли и изоляция нужны даже с демо-аккаунтами.
- Redis при добавлении не становится источником истины; после потери событий нужен
  новый снимок из БД. Полноценная автономная работа отделения без центральной связи
  требует отдельного протокола владения/синхронизации. Локальный кэш сам по себе
  не защищает от двойных назначений; для MVP при отсутствии связи команды недоступны.
- Масштабирование на 40 000 отделений пока не проверено и не рассчитано.
