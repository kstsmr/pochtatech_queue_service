# Правила очереди v1

`config/priority.yaml` записан JSON-синтаксисом, который допустим в YAML 1.2.
Так проверка базовых правил работает на стандартном Python без зависимостей.
Это начальные значения, не доказанные SLA или результат нагрузочного теста.

## Выбор следующего

1. В одной транзакции заблокировать отделение и взять активную версию правил.
2. Зафиксировать одно серверное now для решения. Активировать наступившие booked.
3. Выбрать только waiting нужного отделения с eligible_at <= now, подходящей
   услугой и target_window_id равным текущему окну либо NULL.
4. Вычислить эффективный уровень каждого кандидата по правилам ниже.
5. Взять минимум `(priority_level, queue_sequence)`, назначить окно и записать
   событие с now и rule_version; обновить версию талона. Зафиксировать транзакцию.

Чем меньше уровень, тем выше приоритет. Правила:

- Дедлайн ожидания: eligible_at + max_wait_minutes[source]. При now >= дедлайн
  уровень overdue, который всегда выше бонуса записи. Возврат не сбрасывает дедлайн.
- Для исходной предзаписи eligible_at = scheduled_time - early_minutes.
  Если redirect_count = 0 и now <= scheduled_time + grace_minutes, уровень appointment.
- После grace_minutes предзапись получает late_prebooking.
- QR и walk_in получают одноимённые уровни; в демонстрационных правилах они равны.
- Во всех равных уровнях FIFO строго по исходному queue_sequence.

Запись раньше eligible_at не кандидат вообще, даже при пустой очереди.
При перенаправлении сохраняются eligible_at и FIFO, бонус записи отключается.
Для QR/walk_in eligible_at = created_at. Все сравнения в UTC с точностью БД.

## Почему так

Запись получает приоритет вокруг своего времени. Живая очередь равноправна с QR,
а спустя 20 минут становится выше обычных записей. Также повышается QR и поздняя
предзапись, чтобы не создавать голодание других источников. Среди просроченных
сохраняется FIFO; новые входящие талоны имеют больший sequence и не обгоняют их.

20 минут — порог повышения, не верхняя граница фактического ожидания. При конечном
числе клиентов впереди, работающих совместимых окнах и конечной длительности
обслуживания клиент будет вызван. Закрытые окна, перегрузка и бесконечные возвраты
не позволяют обещать абсолютный предел. Такие случаи видны как отклонения.

## Примеры для тестов ядра

| Ситуация | Ожидаемый результат |
| --- | --- |
| QR и walk_in, оба обычные | Меньший queue_sequence первым |
| now ровно scheduled_time - 10 минут | Запись уже может участвовать |
| now ровно scheduled_time + 15 минут | Бонус записи ещё действует, если нет overdue |
| Теперь позже конца grace | Поздняя запись на обычном уровне |
| walk_in ожидает ровно 20 минут | overdue, впереди обычной записи |
| Два overdue | Меньший queue_sequence первым |
| Более приоритетная услуга недоступна окну | Выбрать следующего совместимого |
| Талон закреплён за другим окном | Пропустить его для текущего окна |
| Возврат и повторный вызов | Сохраняются FIFO и deadline, растёт version |
| Перезапуск | Тот же снимок БД + now + версия правил дают тот же выбор |

## Управление правилами

При первичном создании отделения загружается config/priority.yaml и создаётся
priority_rules version=1. После этого источник настроек — PostgreSQL.
Перезапуск не перезаписывает изменения руководителя файлом.
Admin API создаёт новую версию под блокировкой отделения, прежняя остаётся в истории.
Валидация обязательна до записи: целые числа, диапазоны, полный набор ключей,
overdue строго выше остальных, appointment не ниже обычных уровней.
Противоречивые значения отклоняются целиком; без молчаливого fallback.

Новые max_wait/levels/grace действуют на последующие решения для всех ожидающих.
Изменение early_minutes действует только на новые записи: eligible_at уже выданных
не изменяется. Каждое решение сохраняет фактическую rule_version.
История изменения правил хранит actor_id и created_at.

Базовую проверку файла выполнить из корня: `python3 tools/check_priority.py`.
Тесты валидатора: `python3 -m unittest discover -s tests -v`.
