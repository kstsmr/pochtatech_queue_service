# Алгоритм электронной очереди

## Цели и границы

Алгоритм применяется отдельно внутри каждого отделения. Окно рассматривает
только талон на услугу, которую оно обслуживает. Правила решают четыре задачи:

1. Клиент с записью получает преимущество рядом с назначенным временем.
2. QR-талон и клиент живой очереди сохраняют понятный порядок ожидания.
3. Любой источник после предельного ожидания защищён от дальнейшего вытеснения
   новыми записями.
4. Два окна не могут получить один талон.

Числовые значения находятся в `config/priority.yaml`. Файл является
JSON-совместимым YAML и проверяется при старте. Каждая содержательная правка
получает новый `rule_version`; уже сохранённая версия никогда не перезаписывается.

## Моменты участия в очереди

У каждого талона есть неизменяемые `queue_sequence` и `eligible_at`.

- **Предварительная запись** создаётся в `booked`. Её `eligible_at` равно
  `scheduled_time - early_minutes`. После наступления этого времени сервер
  атомарно переводит талон в `waiting`. В текущей MVP-модели отдельного check-in
  нет: наличие электронного талона считается подтверждением визита. Если клиент
  не пришёл, оператор после вызова фиксирует `no_show`.
- **QR-талон** создаётся в `waiting`; `eligible_at` равно времени выдачи.
- **Живая очередь** создаётся оператором в `waiting`; `eligible_at` равно времени
  добавления.

Активация предзаписи выполняется перед каждым вызовом и при чтении клиентом
своего талона. Поэтому пропущенный таймер или перезапуск сервера не теряет
запись: решение восстанавливается из времени в PostgreSQL.

## Эффективный уровень

Меньшее числовое значение означает более высокий приоритет. Для каждого
ожидающего совместимого талона сервер вычисляет уровень в следующем порядке:

1. `overdue`: время от `eligible_at` достигло `max_wait_minutes` его источника.
2. `appointment`: предзапись находится между `scheduled_time - early_minutes`
   и `scheduled_time + grace_minutes`.
3. `late_prebooking`: grace-интервал предзаписи закончился.
4. `qr`: обычный QR-талон.
5. `walk_in`: обычная живая очередь.

Проверка `overdue` выполняется первой. Поэтому клиент живой очереди после
`max_wait_minutes.walk_in` не может быть вытеснен новой записью ко времени.
Несколько просроченных клиентов обслуживаются в порядке их `eligible_at`.

Демонстрационная конфигурация задаёт одинаковый обычный уровень для QR, живой
очереди и опоздавшей записи. Значит, до срабатывания защиты они образуют общий
FIFO. Эти уровни можно разделить конфигурацией без изменения кода.

`max_wait_minutes.prebooking` обязан покрывать весь интервал
`early_minutes + grace_minutes`. Это исключает ситуацию, когда запись становится
`overdue` ещё внутри своего временного окна.

## Полный ключ выбора

Для конкретного окна кандидаты сортируются по кортежу:

```text
(
  effective_priority,
  eligible_at,
  queue_sequence,
  ticket_id
)
```

`eligible_at` задаёт FIFO по моменту фактического допуска. `queue_sequence` и
`ticket_id` являются детерминированными разрешителями равенства. Внутри одного
уровня результат воспроизводим при одинаковом снимке БД и времени запроса.
Направление в конкретное окно только исключает талон из кандидатов остальных
окон и не даёт ему дополнительного приоритета.

## Атомарный вызов

`POST /api/staff/windows/{window_id}/call-next` выполняется одной транзакцией:

1. Блокируется строка окна и проверяются его состояние, владелец и отсутствие
   активного талона.
2. Созревшие предзаписи переводятся в `waiting`, для каждой пишется событие.
3. Читается одна активная версия `priority_rules` и проверяется её структура.
4. Выбирается первый совместимый кандидат через
   `FOR UPDATE OF t SKIP LOCKED`.
5. Талон получает `called`, окно и номер версии правил; изменение пишется в
   `ticket_events` в той же транзакции.

Частичный уникальный индекс `one_active_ticket_per_window` запрещает более одного
талона в `called` или `serving` на окно. Строковая блокировка талона исключает
двойной вызов одного клиента параллельными окнами. `SKIP LOCKED` позволяет второму
окну без ожидания выбрать следующего кандидата.

## Переходы и спорные ситуации

```text
booked -> waiting -> called -> serving -> served
                    |   |       |
                    |   +-------+-> waiting (return / redirect)
                    +-------------> no_show
booked|waiting --------------------> cancelled
```

- **Возврат** сохраняет исходные `eligible_at` и `queue_sequence`. Клиент не
  теряет уже накопленное ожидание.
- **Перенаправление** сохраняет возраст талона, меняет услугу и при необходимости
  задаёт целевое окно. При смене услуги прежний слот освобождается. Источник
  остаётся прежним и виден сотруднику.
- **Повторный вызов** обновляет `called_at`, но не меняет источник или очередь.
- **Неявка** фиксируется оператором явно. Автоматическое закрытие не используется,
  чтобы задержка сотрудника не лишила присутствующего клиента талона.
- **Закрытие свободного окна** происходит сразу. Окно с активным клиентом
  переходит в `draining`, не вызывает новых клиентов и закрывается после
  завершения, возврата, перенаправления или неявки. У ожидающих талонов,
  направленных в закрывшееся окно, атомарно снимается `target_window_id`; они
  продолжают участвовать в общей очереди с прежними `eligible_at` и
  `queue_sequence`.
- **Недоступная услуга** не участвует в выборе этого окна. Если совместимых
  кандидатов нет, API возвращает контролируемый `queue_empty`, не меняя данные.

## Позиция и ожидаемое время

Позиция клиента считается среди ожидающих талонов той же услуги по тому же
`effective_priority`, `eligible_at` и FIFO-ключам, что и вызов. В оценку времени
входят уже вызванные и обслуживаемые клиенты этой услуги, средняя длительность
услуги и число открытых совместимых окон:

```text
ceil((клиенты впереди + активные клиенты) * среднее время / max(открытые окна, 1))
```

Это базовый прогноз, а не обещание SLA: будущая запись ко времени, закрытие окна
или перенаправление могут изменить порядок. Направление в конкретное окно в
общей клиентской позиции не моделируется, поэтому оценка остаётся консервативной.

## Гарантии и ограничения

- Внутри одинакового уровня сохраняется FIFO по моменту допуска.
- После достижения max wait новые обычные и appointment-талон не обходят клиента.
- Абсолютное время обслуживания невозможно гарантировать при отсутствии
  совместимого открытого окна или если входящий поток превышает пропускную
  способность. Это операционное ограничение явно отделено от гарантии алгоритма.
- Состояние, версии правил и журнал находятся в PostgreSQL и переживают рестарт.
- Все переходы талона и окна журналируются с актором, версиями и состояниями до
  и после изменения.

## Демонстрационные значения

В `config/priority.yaml`: предзапись активируется за 10 минут, grace-период
составляет 15 минут, живая очередь становится overdue через 20 минут, QR и
предзапись — через 30 минут. Уровни: `overdue = 0`, `appointment = 1`, обычные
источники и опоздавшая запись — `2`.
