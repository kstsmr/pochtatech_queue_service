# Алгоритм приоритета очереди

## Цели

Алгоритм сохраняет FIFO внутри одного уровня, учитывает время предварительной
записи и не позволяет клиентам живой очереди ждать бесконечно. Все числовые
параметры находятся в `config/priority.yaml` и могут меняться без правки логики.

## Правила выбора

1. Предзапись становится доступной для вызова за `early_minutes` до
   `scheduled_time`. До этого талон имеет статус `booked` и не участвует в
   выборе.
2. В интервале от `scheduled_time - early_minutes` до
   `scheduled_time + grace_minutes` предзапись имеет уровень `appointment`.
3. QR-талон участвует в обычном FIFO с момента создания.
4. Клиент, добавленный оператором, начинает с уровня `walk_in`. После
   `max_wait_minutes.walk_in` его уровень повышается до `overdue`.
5. Просроченные QR-талон и предзапись аналогично получают уровень `overdue`
   согласно своим `max_wait_minutes`.
6. Опоздавшая предзапись после grace-интервала получает уровень
   `late_prebooking` и больше не вытесняет пришедших вовремя.

Кандидаты сравниваются по кортежу:

```text
(уровень приоритета, eligible_at, queue_sequence)
```

Меньшее значение уровня обслуживается раньше. `queue_sequence` монотонен и
обеспечивает воспроизводимый FIFO при равных остальных полях.

## Конкурентность и окна

Вызов следующего талона должен выполняться в одной транзакции PostgreSQL с
`SELECT ... FOR UPDATE SKIP LOCKED`. Частичный уникальный индекс
`one_active_ticket_per_window` запрещает более одного активного талона в окне,
а блокировка строки талона исключает двойной вызов из разных окон.

Закрытие окна без активного клиента выполняется сразу. При активном клиенте
окно переводится в `draining`: новый талон не назначается, текущий обслуживается
до завершения или явно возвращается оператором в очередь. Все переходы
фиксируются в `ticket_events` или `window_events`, поэтому состояние
восстанавливается из PostgreSQL после перезапуска сервиса.

## Демонстрационная конфигурация

Файл `config/priority.yaml` содержит версию схемы, интервалы активации и
ожидания, уровни источников и таймаут вызова. Активная копия конфигурации также
хранится в `priority_rules`, чтобы событие можно было связать с конкретной
версией правил.
